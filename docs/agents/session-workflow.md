# Running a producer session

Moved from AGENTS.md (section 4). Back to the router: [AGENTS.md](../../AGENTS.md). The orchestrator's full procedures (starting a session, keeping it alive, delivering it) are in [docs/ORCHESTRATION.md](../ORCHESTRATION.md); this is the short version.

1. Create `sessions/NNN-shortname/` and write the brief into `PROMPT.md` there (see `docs/ORCHESTRATION.md`).
2. Fill in `prompts/producer.md` (placeholders in `{{...}}`) and run it as a sub-agent with file, shell and image-reading tools. A full session is 25-45 iterations, about 30-60 minutes.
3. When it finishes: check the master report (genre, LUFS, true peak under -1 dBTP, no warnings), check the length against the genre (see "Genre conventions" in docs/ORCHESTRATION.md), copy `final.mp3`, and write the session `README.md` (see `sessions/001-bleachers/README.md` for the format).
4. Back up a running session at every check-in: `python3 tools/backup_sessions.py push <NNN>` (private bucket, `sessions-wip/`; `pull <NNN>` restores). Until it is published, a session exists only on this machine. Long sessions can be interrupted (for example when the operator's own turn is interrupted). Check on them periodically; to resume, start a fresh producer agent with the same prompt plus "read journal.md and the helper scripts, listen to the latest render, continue numbering". Forward-only versioning makes this seamless.
5. **After every genre switch, record lessons in the repo** (owner's standing rule): add the session entry to `docs/LESSONS.md` and update its "Across genres" section with what transferred and what didn't. If the new genre needed research, save it as a `docs/<GENRE>.md` brief (see `docs/ROMANIAN.md`, `docs/UKRAINIAN.md`). Commit these with the session.
6. Sessions can run in parallel (one folder each). Engine changes made while another session is rendering must be additive and written atomically (write a temp file, then rename), so a running render never imports a half-written module.
7. **Publish**, only after the owner has listened to and approved the master (ORCHESTRATION.md standing rule 21), with `python3 tools/upload_track.py <id> --owner-approved` ([track-storage.md](track-storage.md)) once its line is in `site/data/tracks.json`: the session's files go to the S3 bucket, not into git (without a bucket: the tool uploads nothing, lists the files and you send them to the user in the chat; [track-storage.md](track-storage.md), "Without a bucket") (renders never leave the workspace; they are reproducible from `project.json`, because rendering is seeded and deterministic). Commit `site/data/tracks.json` (it now carries the track's uuid) and the cross-track files (docs, engine, lessons).

## In your own clone (a fork or a fresh clone, run by someone other than the owner)

The steps above are the owner's workspace. In your own clone the person you work for is the owner of the session: they give the brief and judge the result by ear. What changes:
- **Setup:** a virtual environment and `tools/setup.sh --required` ([engine-setup.md](engine-setup.md), "Requirements"), then the smoke test. Optional resources left as `todo` don't block a track.
- **Session folder:** `sessions/<NNN>-<name>/` as above, numbered from 101 so it never shares an id with the owner's published tracks in `site/data/tracks.json` (001-0NN). `sessions/` is git-ignored: nothing of the session is committed.
- **The brief:** fill `prompts/producer.md` from the genre's row in docs/ORCHESTRATION.md "Genre conventions" (`{{REPO}}` is the clone's absolute path). The template asks for the READMEs of earlier tracks in `sessions/*/README.md`; a fresh clone has none, so point it at `examples/showcase/*/session/README.md` (those two PROMPT.md files show filled briefs, with the owner's paths in them). Run it as a sub-agent that has file, shell and image-reading tools; without sub-agents, the agent you talk to can follow PROMPT.md itself.
- **Skip** what needs the owner's resources: `backup_sessions.py` and `upload_track.py` (both need the owner's bucket; without variables they skip or refuse), `site/data/tracks.json`, the website, `docs/LESSONS.md` entries and commits, and the scheduled check-ins (a Claude Code cloud feature; elsewhere, just check the session's `renders/` and `journal.md` from time to time).
- **What you get**, all in the session folder: `final.mp3` (the master; play it in any audio player), `journal.md` (every decision), `project.json` (reproduces the track: `studio.py render` with `BEAT_DIR` set to the folder), `renders/vNNN.master.png` and `.report.json` (the master's tonal balance and numbers), and `ear.png` (the last thing Spectre listened to). Delete `renders/*.wav` when you are done with the session; they are reproducible from `project.json`.
- **Cost:** setup a few minutes and 3 GB of downloads (packages and models); a full session 30-90 minutes of agent time, 25-45 render-and-listen iterations, and a long agent context (the manual, the genre brief and the lessons are about 100k tokens to read before the first render, and every listen adds an image). It needs an agent subscription or API budget that allows that; the engine itself is quick (a render of a 75-second piece about 5-15 s, a listen 10-20 s, a master about 1 minute on a 16 GB cloud container), so the time goes into the agent's reading and thinking.
